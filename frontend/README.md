# frontend/ — PMS 웹 클라이언트 (백엔드 실연동)

`pms/` 앱의 구현된 API에만 붙는 React + TypeScript 클라이언트다.
디자인(팔레트·레이아웃·컴포넌트 클래스)은 이전 프로토타입의 `styles.css`를 그대로
쓰고, 데이터·상태·API 계층은 현재 백엔드 계약(PRD-pms §7)에 맞춰 새로 썼다
(2026-08-22).

> 기획 검증용 목업 앱은 `prototype/`이다(백엔드 없음, PRD v2.4 화면 전체).
> 이 앱은 그 반대다 — **실제로 동작하는 것만** 있다.

## 실행

```bash
docker compose -f ../pms/docker-compose.yml up -d   # PostgreSQL
(cd ../pms && ./gradlew bootRun)                    # 백엔드 :8080
npm install && npm run dev                          # 이 앱 :5173
```

`vite.config.ts`가 `/api` 요청을 `localhost:8080`으로 프록시하므로 CORS 설정이 없다.

로그인: 시드 계정 이메일 + `proten1!` (로그인 화면의 시드 계정 4행 = 권한 그룹별 화자
— 관리자·부문장·팀장·팀원).

## 로그인을 건너뛰고 쓰기 (개발 모드)

인증이 꺼진 기본 설정에서는 서버가 `X-Caller-Person-Id` 헤더만 보므로 **로그인 없이
화자만 지정해** 나머지 기능을 볼 수 있다.

- 로그인 화면 시드 계정 행의 **`바로 시작`** 버튼 → 그 사람으로 즉시 진입
- 또는 아래 **`로그인 없이 둘러보기`** 카드에 personId(시드 1~43)를 넣고 시작
- 진입 후에는 상단 바의 **화자 셀렉트**로 로그아웃 없이 사람을 바꿀 수 있다.
  목록은 *지금까지 본 인원의 누적 명부*라 가시성이 좁은 화자로 옮겨도 되돌아올 수
  있고, 명부에 없는 사람은 옆의 `id` 칸에 personId를 직접 넣는다.

이 모드는 헤더를 신뢰하므로 **개발용이다.** 인증을 켜면 서버가 401로 막고 화면은
"인증이 켜져 있어 화자 지정으로는 들어갈 수 없습니다"라며 로그인으로 되돌린다.
없는 personId를 넣으면 404를 받아 같은 방식으로 되돌린다.

## 인증 두 모드를 모두 지원한다

백엔드 스위치 `pms.auth.enabled`가 어느 쪽이든 같은 화면이 동작한다.

| 스위치 | 서버가 보는 화자 | 이 앱이 보내는 것 |
|--------|------------------|-------------------|
| `false` (기본) | `X-Caller-Person-Id` 헤더 | 로그인 세션: 토큰 + 헤더 / 화자 지정 세션: 헤더만 |
| `true` | access 토큰의 `sub` | 같음 — 헤더는 서버가 무시하고, 화자 지정 세션은 401이다 |

로그인·갱신 라우트는 두 모드에서 모두 열려 있어서, 어느 쪽이든 로그인해서 받은
토큰의 `sub`를 헤더로도 실으면 배선이 하나로 끝난다(`src/api.ts`).
**인증 OFF는 헤더를 신뢰하는 개발 모드다 — 그대로 외부에 노출하면 안 된다.**

인증을 켜고 확인하려면:

```bash
(cd ../pms && ./gradlew bootRun --args='--pms.auth.enabled=true')
```

## 붙어 있는 기능

| 화면 | 서버 | AC |
|------|------|-----|
| 로그인 | `POST /api/auth/login`·`/refresh` | 401 실패 문구는 사유를 구분하지 않는다 |
| 홈 | 목록 2종 집계 | — |
| 프로젝트 목록 | `GET /api/projects` (§7 page 봉투) | A3-1 |
| 프로젝트 상세 | `GET /api/projects/{id}` | A3-2·A3-3 (파생 phase 포함) |
| 새 프로젝트 | `POST /api/projects` | A1-1~A1-6 (PM 1명 필수) |
| 상태 전이 | `PUT /api/projects/{id}` | A5-1 — 상세 화면의 **전용 버튼 + 확인 카드**, 다음 한 칸만(계약대기→수주확정→진행중) |
| 정보 수정 | `PUT /api/projects/{id}` | A5-1~A5-3 — 폼은 **status를 다루지 않는다**(입구를 하나로) |
| 진척률 | `PUT /api/projects/{id}/progress` | A2 — **진행중에서만**(A2-9) · 100%만 확인 모달(2026-08-09 ①) |
| 완료 처리·재개 | `POST /{id}/complete`·`/reopen` | A7-1~A7-5 |
| 배정 추가·수정·종료 | `POST /{id}/assignments` · `PUT`·`DELETE /api/assignments/{id}` | B1-1·B1-2·B1-4·B2-1 |
| PM 교체 | `PUT /api/projects/{id}/pm` | A6-1 (미배정이면 배정도 생성) |
| 프로젝트 삭제 | `DELETE /api/projects/{id}` | A4 — PM 또는 생성 권한자 |
| 인력 목록·등록·삭제 | `GET`·`POST`·`DELETE /api/people` | 가시성 범위 · E2-1·E2-3(관리자만) |
| 인력 수정·소속 이동 | `PUT /api/people/{id}` · `PUT /{id}/org-unit` | E2-2 · E1-1 — 소속만 바뀌면 이동 라우트로 보내 **E1-2 경고**를 받아 보여 준다 |
| 조직 목록·추가·개명·삭제 | `GET`·`POST`·`PUT`·`DELETE /api/org-units` | E3-1·E3-2 · E3-3 빈 노드만(관리자만) |
| 직급 관리 | `GET`·`POST`·`PUT`·`DELETE /api/grades` | E4 — 계수는 보정 가동률 가중치 · 0명일 때만 삭제 |
| 권한 그룹 관리 | `GET`·`POST`·`PUT`·`DELETE /api/permission-groups` | E5 — 가시성 select + 기능 토글 4종 · **관리자 그룹은 버튼 잠금**(자기 잠금 방지) |
| 알림 벨·읽음 | `GET /api/notifications` · `PATCH /{id}/read` | F1-3 — 미읽음 뱃지 · 벨을 열 때 재조회 |
| 알림 설정 | `GET`·`PUT /api/me/notif-prefs` | H1-4 — 유형 5종 on/off(전체 교체) |
| 유지보수 계약 등록·수정 | `POST`·`PUT /api/maintenance/contracts[/{id}]` | D2-1·D2-2 — **"계약 관리" 플래그**만 · 삭제 없음(종료는 상태로) |
| 사이트 등록·수정 + 연락처 | `POST /contracts/{id}/sites` · `PUT /api/maintenance/sites/{id}` | D2-4 — 연락처는 **전체 교체**, 원문(raw)은 서버가 조각으로 조립 |
| 프로젝트·배정 기간 | 생성·수정 폼 | 종료일 > 시작일 (400 field=endDate) |
| 내 권한 | `GET /api/me` | 버튼 노출 판정의 근거 |
| 가동률 | `GET /api/utilization` | C1-1~C1-6 — 월 선택 · 팀 필터 · 기본/보정 · **과부하만 보기**(서버 필터) |
| 유지보수 계약 목록·상세 | `GET /api/maintenance/contracts` (+`/{id}`) | D4-1·D4-2 — keyword는 계약명·계약사·**사이트명** 3종(서버 필터) |
| 유지보수 이슈 목록 | `GET /api/maintenance/issues` | D3-4 — 담당자·고객사 상시 노출 · 내 담당/**미배정** 필터 |
| 감사 로그(통합) | `GET /api/audit` | G1-3 — 관리 플래그 없으면 403(화면이 그대로 보여 준다) |
| 프로젝트 이력 탭 | `GET /api/projects/{id}/audit` | G2-2 — 가시성 안이면 역할 무관(G2-3) |

에러는 §7 봉투(`{error:{code,message,field,traceId}}`)를 그대로 화면에 보여 준다 —
403 "담당자만 가능" · 404 은닉 · 409 `STALE_VERSION`(상세를 다시 읽어 최신 version을
채운다) · 409 `IN_USE` · 422 `INVALID_ROLE`·`IMMUTABLE_ACCOUNT` 등. code를 함께
표시하므로 사용자가 그대로 신고할 수 있다.

## 권한에 따른 버튼 노출

`GET /api/me`의 플래그와 상세의 배정 역할로 **누를 수 없는 버튼을 감춘다**
(`src/permissions.ts` — 상위 PRD §4-2 표의 표시용 사본, 최종 판정은 서버).

| 버튼 | 보이는 조건 |
|------|-------------|
| + 새 프로젝트 | "프로젝트 생성" 플래그 |
| 정보 수정 · 상태 전이 | 그 프로젝트의 PM·PL |
| 진척률·완료 처리·재개 | 그 프로젝트에 배정된 인원 |
| 배정 추가·M/M 수정·종료·PM 지정 | 그 프로젝트의 PM |
| 프로젝트 삭제 | PM 또는 "프로젝트 생성" 플래그 |
| 인력 등록·수정·삭제 · 조직 추가·개명·삭제 · 직급·권한 그룹 관리 | "사용자/조직/권한 관리" 플래그 |
| 유지보수 계약·사이트 등록·수정 | "계약 관리" 플래그 (관리자·부문장·팀장) — 조회는 전사 공개인데 쓰기만 갈린다 |

"전 프로젝트 관리" 플래그 보유자(기본: 관리자)는 모든 프로젝트에서 PM으로 간주된다
(§4-1 치환) — 화면도 같은 치환을 따른다.

## 아직 없는 것 (서버에 없어서)

- **AI 어시스턴트 패널** — 챗 BFF(`/api/chat`) 대기.
- **알림 SSE 즉시 갱신** (F1-4) — 라우트가 없어 벨은 **부팅 때와 벨을 열 때** 다시
  읽는다. 폴링은 두지 않았다(44명 규모에 끊임없는 요청이 되고, SSE가 할 일을 어설프게
  흉내 낸다). 스트림이 열리면 `NotificationBell`의 그 자리가 구독으로 바뀐다.
- **유지보수 이관(D1)·이슈 쓰기(D3-1~D3-3)** — 서버 라우트 대기. 계약·사이트
  쓰기(D2)는 2026-08-24에 붙었다.
- **역할 지정(A6-3)·프로젝트별 권한(A8)** — 서버 라우트 대기.
- **서버 이름 검색·`?phase=` 필터** — 목록을 한 번에 받아 화면에서 거른다(시드 382건
  기준의 임시 선택. `src/api.ts`의 `LIST_PAGE_SIZE` 주석이 되돌리는 트리거다).

## 구조

```
src/
├── types/api.ts     서버 DTO 타입 (이름은 백엔드 DTO와 일치)
├── api.ts           fetch 래퍼 + 세션(토큰·화자) + 엔드포인트 — 화면은 fetch를 직접 부르지 않는다
├── store.tsx        세션·라우팅·데이터 로딩·쓰기 동작 (Result로 §7 봉투 전달)
├── permissions.ts   버튼 노출 판정 (표시용 — 서버가 최종 판정)
├── labels.ts        열거 값 → 한국어 표기(정본은 서버 enum의 label())
├── theme.ts         라이트/다크 토글
├── styles.css       디자인 원본 (구 프로토타입에서 그대로 이식)
├── components/      UI 조각 · 진척률 편집기 · 배정 패널 · 조직 패널 · 감사 표 · 모달 · 화자 전환
└── views/           로그인 · 홈 · 프로젝트 목록/상세 · 인력·조직 · 가동률 · 유지보수 계약/상세 ·
                     유지보수 이슈 · 감사 로그
```

**감사 표는 두 화면이 공유한다**(`components/AuditTable.tsx`): 통합 로그와 프로젝트
이력이 **같은 행**을 다른 필터로 보여 주므로(별도 저장 없음 — G1-1·G1-2), 표를 두 벌
만들면 같은 데이터가 두 모양으로 보인다.

**화면 3종은 라우트에 들어올 때 조회한다**(부팅 때 미리 받지 않는다): 가동률은 질의에
기준 월이 있어 부팅 시점에 고를 값이 없고, 감사는 플래그가 없으면 403이며, 유지보수는
105계약을 홈에서 미리 받을 이유가 없다.

## 검증

```bash
npm run typecheck    # tsc --noEmit (verify.sh의 frontend 단계가 이걸 돌린다)
npm run build        # 타입 검사 + 프로덕션 번들
```

Vitest 단위 테스트는 아직 없다 — `npm test`는 지금 타입 검사에 연결돼 있고,
로직(파서·상태 전이)이 생기면 그때 테스트를 붙인다(conventions §5).
