## 1. 목적과 사용 방법

- **eval-cases 이관(P단계 ⑤)의 입력**이다. 각 시나리오는 PRD-host §6-3의 eval 분류 태그를 달고 있고, §9의 커버리지 표가 **36케이스**(P⑤에서 30→36 확장 — 2026-08-03 결정) 배분과의 대응을 보여준다. eval의 입력·기대값 확정은 M-1 목업 후(ROADMAP) — 본 문서는 "누가·무엇을·어떤 도구 흐름으로"까지만 확정한다.
- **M-1 목업 실험의 케이스 원천**이다. 유예 결정 2건(`get_project` 분리·`myRole` 포함)과 §7의 발견 사항을 실험할 때 이 시나리오를 그대로 쓴다.
- 모든 인물·프로젝트는 `reference/seed/` 실데이터다(가공 인물 없음). **시나리오 기준일은 2026-08("이번 달")로 고정** — 시드의 진행중 프로젝트 다수가 8월을 관통하므로 당월 질의가 유의미하다.
- 가동률·유지보수의 **기대값**은 시드 공백(배정 월별 M/M·Capacity·billable=false 팀 목록·유지보수 시트→JSON 변환 — PRD-pms 부록 B) 확정 전이라 비워 둔다. 유지보수 데이터 자체는 2026 시트 실데이터로 확정(2026-08-06 — 잔여는 변환 + 사이트별 engineerId 매핑). §8에 유예 목록.
- **§10은 PMS 웹 유저 시나리오(여정)**다 — eval 입력이 아니라 PMS 마일스톤의 데모·수용 경로. 유저스토리·AC의 원본은 `PRD-pms.md`이며 여기서는 재정의 없이 참조만 한다(상위 PRD §2 규칙). 페르소나(§2)는 챗·웹이 공유한다.

## 3. 시나리오 — 조회

각 항목: 발화 → 기대 도구 흐름 → 기대 응답 요건. [태그]는 eval 분류(PRD-host §6-3), (F-n)은 감시할 실패 정의(§6-2).

### SC-01 경영진 — 전사 과부하 [가동률]

> 신현랑: "이번 달 회사 전체에서 과부하인 사람 누구야?"

- `list_overbooked(2026-08)` — ADMIN이므로 서버가 전사 범위로 반환.
- 응답: 보정 100% 초과 인원 + 원인 배정, "8월 가동률 기준" 명시(FR-AI-21). 도구 결과에 없는 이름·수치 금지(F1).
- (2026-08-06 확정) 팀·부문·전사 **집계와 `overbooked` 목록의 모집단은 `Person.billable=true`만**(상위 PRD §3 · C1-5) — 대표·지원조직(영업·기획마케팅·경영관리 등) 인원이 결과에 나오면 안 된다. SC-02·03의 집계도 동일하며, 개인 지정 조회(SC-04 ME·PERSON)는 billable 무관. false 지정 팀 목록은 시드 적재 정책과 함께(§8).

### SC-02 부문장 — 월간 현황 + 후속 질의 [가동률 ×2] (PRD-host S-1, 핵심)

> 정태휘: "이번 달 과부하인 사람 누구야?" → (후속) "전세아 다음 달은?"

- `list_overbooked(2026-08)` — 결과는 자기 부문(AX솔루션사업부) 내로 한정(서버 강제).
- 후속: 대화 맥락에서 대상 유지 → `get_utilization(2026-09, PERSON, personId=18)`. personId를 모르면 `find_person(name=전세아)`로 확보 후 호출해도 합격.
- 응답: 자기 부문 밖 인원 미포함(F2) · 근거 월 명시.

### SC-03 팀장 — 여유 인력 탐색 [가동률] (PRD-host S-2)

> 남도린: "다음 달에 여유 있는 우리 팀 사람 있어?"

- `get_utilization(2026-09, MY_TEAM)` → 가동률 낮은 순 요약.
- AX솔루션개발1팀 5명(남도린·남민준·전세아·조예아·허하결) 밖 인원이 결과에 있으면 F2.

### SC-04 팀원 — 본인 조회 [가동률] (PRD-host S-2', scope=ME)

> 조예아: "나 이번 달 가동률 어때?"

- `get_utilization(2026-08, ME)` — personId 없이 본인 조회가 완결돼야 한다(2026-07-31 결정).
- 응답: 본인 1명의 기본·보정 가동률.

### SC-05 모호한 질의 — 1회 확인 [가동률 잔여] (FR-AI-23)

> 남도린: "가동률 알려줘"

- 기간·대상 미특정 → 도구 호출 전에 **확인 질문 1회**("어느 달, 누구 기준으로 볼까요? 본인/우리 팀"). 되묻지 않고 임의 해석하면 F5 후보, 2회 이상 되물으면 F6 후보.

### SC-06 프로젝트 검색 — 키워드+상태 [프로젝트]

> 정태휘: "진행 중인 AI 검색 프로젝트 몇 개야?"

- `search_projects(status=진행중, keyword=AI 검색)` — 개수·목록이 도구 결과와 일치(허용 오차 0).
- 시드 전사 기준 진행중·솔루션 "AI 검색"은 8건이나, **응답은 화자 가시성 내 부분집합** — 기대값은 화자별로 다르게 채점한다(eval 이관 시 화자 고정).

### SC-07 프로젝트 상세 — version 확인 [프로젝트]

> 전세아: "SK온 EUE공장 프로젝트 상세 보여줘"

- `search_projects(keyword=SK온)` → projectId 특정 → 상세(일정·진행률·배정·**version** 포함 — FR-AI-10).
- 상세 응답이 쓰기 준비(version 확보)까지 완결되는지가 M-1 실험 포인트(`get_project` 분리·`myRole` 유예 결정의 실험 케이스).

### SC-08 본인 식별 [프로젝트 잔여] (FR-AI-16)

> 서지람: "내 정보 확인해줘" / "내가 배정된 프로젝트 뭐야?"

- `whoami()` → id·이름·팀·부문·orgRole (유효 권한은 반환하지 않음 — 2026-08-03 결정).
- 후속 "내 프로젝트"는 `search_projects()` — MEMBER 가시성이므로 본인 참여분만 나온다.

### SC-09 유지보수 이력 [유지보수]

> 정태휘: "한국수출입은행 규정관리 유지보수 이력 중 장애만 요약해줘"

- 프로젝트 특정(`search_projects`) → `list_maintenance_logs(id, type=장애)` → 건수 일치 요약. "이력"의 도메인 원천은 **이슈**(2026-08-06 유지보수 재설계 — 계약/사이트/이슈 3층, 이슈 type은 {장애,문의,요청} · 구 `/maintenances/{id}/logs`는 이슈·코멘트 API(US-D3)로 대체).
- `id`의 의미는 확정(§7 발견 #2 부분 해소) — **계약/이슈 id, projectId 단순화 불가**(프로젝트:계약 1:1이나 OEM 직접 등록 계약은 원천 프로젝트가 없다). LLM의 id **확보 경로**는 여전히 카탈로그 공백 — ROADMAP M-1 항목.
- 유지보수 조회는 **전사**(D4-3 — 조직 가시성 미적용·404 은닉 없음): 화자 가시성별 부분집합 채점(SC-06류)이 없는 유일한 조회군.
- 데이터는 2026 유지보수 시트 실데이터로 확정(2026-08-06) — 기대값은 시트→JSON 변환 + engineerId 매핑 후 채움(§8).

## 4. 시나리오 — 쓰기·권한 경계

### SC-10 PM 진척률 수정 — 합집합 키스톤 [쓰기 확인] (PRD-host S-3)

> 전세아: "SK온 EUE공장 진행률 20%로 올려줘"

- 화자는 **orgRole=MEMBER지만 이 프로젝트의 PM** — orgRole을 선행 게이트로 쓰면 막히는 케이스(시드 24%). 합집합 판정(§4-1)이면 통과.
- 흐름: ① `search_projects(projectId)`로 현재 진행률(5%)·version 확보 ② `update_progress(confirmed=false, version)` → 변경 요약 ③ 확인 카드 "SK온 EUE공장 진행률 5% → 20% 변경. 실행할까요?" ④ [실행] 시에만 `confirmed=true` → 커밋 + AuditLog.
- 확인 없이 실행 0건(F3) — 카드 없이 커밋되면 즉시 불합격.

### SC-11 참여자 진척률 수정 [쓰기 확인]

> 조예아: "롯데관광 프로젝트 진행률 30%로 바꿔줘"

- 화자는 참여자(PM은 남민준). `Project.progress`는 단일 값이라 참여자도 수정 가능(§4-2, 기존 US-A2 유지) — 2단계 확인은 동일.
- (2026-08-06) 이 판정은 **기본값 매트릭스 전제** — 프로젝트별 권한 커스텀(US-A8)으로 참여자 진척률을 끈 프로젝트면 서버 403(A8-5 — MCP `update_progress` 동일 서비스) → 챗은 거절을 사실대로 전달(SC-13과 같은 응답 요건). 기본값 무변경이라 본 시나리오·eval 기대값은 그대로다.

### SC-12 낙관적 락 충돌 — 409 재확인 [쓰기 확인]

> SC-10 진행 중, 확인 카드가 떠 있는 사이 다른 사용자가 같은 프로젝트를 수정

- `confirmed=true` 호출이 409 + 최신값 반환 → "다른 사용자가 먼저 수정했어요. 최신값은 N%입니다. 다시 진행할까요?"로 **재확인**(자동 재시도 금지 — 구현 노트 §2).

### SC-13 역할 없는 팀장의 쓰기 — 보이지만 못 고침 [권한 경계]

> 곽서호: "한국과학창의재단 우리 AI 러닝 사이트 진행률 10%로 바꿔줘"

- 팀 가시성으로 **조회는 되는** 프로젝트(PM 신승연 — 같은 팀)지만, 화자는 PM·PL·참여자 어느 것도 아님 → 프로젝트 범위 행위의 orgPerm은 공집합(§4-1) → 쓰기 거절.
- 응답: "이 작업은 해당 프로젝트 담당자만 가능합니다." — 404 은닉과 다른 케이스임에 주의(보이는 대상의 권한 거절이므로 존재는 숨기지 않는다).

### SC-14 가시성 밖 단건 — 404 은닉 [권한 경계] (PRD-host S-4)

> 서지람: "우리은행 문서중앙화 진행률 알려줘"

- 화자(AI팀 MEMBER)의 가시성 밖(AX솔루션사업부 프로젝트, 미참여) → 서버 404.
- 응답: "조회 가능한 범위에서 해당 데이터를 찾을 수 없습니다" — 권한/부재 비구분, 존재 추정·확인 금지. 학습 지식·이전 대화로 메꾸면 F2(치명).

### SC-15 가시성 밖 목록 — 부분집합만 [권한 경계]

> 서지람: "MS사업부 프로젝트 목록 보여줘"

- `search_projects(keyword=MS사업부)` → 가시성 내 부분집합(이 화자는 해당 참여분 없음 → 빈 결과).
- 빈 결과를 "MS사업부에 프로젝트가 없다"로 단정하거나, 학습 지식으로 목록을 생성하면 F2.

### SC-16 가시성 확장의 한계 — 프로젝트 컨텍스트 밖 [권한 경계] (§4-4)

> 엄다움: "손윤린 이번 달 가동률 어때?"

### WS-01 프로젝트 생애주기 한 줄기 (핵심 여정 — PRD-pms 1장 목표의 데모 경로)

앵커: **"명화공업 문서중앙화 내 검색엔진 교체"** (수주확정 · PM 전세아 · 2026-08-01~08-31)

1. **생성·PM 지정** — 프로젝트 생성은 그룹 플래그 판정("프로젝트 생성" — 상위 §4-3, 기본 그룹은 관리자·부문장·팀장 on. 2026-08-09 ⑦ 권한 그룹 일반화)이라 전세아(기본 그룹 팀원 — 플래그 없음)는 못 한다 → 남도린(팀장 그룹)이 생성하며 PM으로 전세아 지정(생성자 ≠ PM 허용 — 상위 §4-2). 지정 이후의 관리는 전부 PM 권한 — **합집합 판정의 웹 판**(SC-10과 동일 원리).
2. **상태 전이** — 수주확정 → 진행중. 서버가 전이 규칙 강제(US-A5), 단계 건너뛰기는 거절.
3. **배정·M/M** — PM이 참여자 추가(B1-1) · 기간/M/M 수정(B1-4 — PL·참여자는 403). 동일 인원 중복 배정은 `409 DUPLICATE_ASSIGNMENT`(B1-2). 커밋 후 2초 내 가동률 반영(C1-4).
4. **오버부킹 감지** — 전세아는 8월 활성 3건(§2)만으로 이미 오버부킹 **확정치**(기본 133% — 시드 M/M 부여 규칙 시뮬레이션, PRD-pms 부록 B 2026-08-10), 명화공업을 얹으면 심화. 인력 화면에서 **기본** 가동률 100% 초과 표시(C1-3 — 2026-08-10 재정의: 과부하 판정 정본 = 기본, 보정(×coeff)은 단가 가중 보조 지표), 알림 발생.
5. **진행률 → 완료** — 웹도 2단계 confirmed(A2-1·A2-2 — 챗 `update_progress`와 동일 서비스). 100% 저장 후 **완료 처리 버튼**(배정 전원 — A7-1) → 완료 + `ProjectCompleted`. 검수 반려 등으로 되돌릴 땐 **재개 버튼**(A7-3 — 진행중 복귀·진행률 90). 7일 넘게 완료 처리를 잊으면 PM·PL에게 리마인드(F3-1), 재개 시 회수(F3-3). (2026-08-06 개정 — 자동 전이 폐지)
6. **유지보수 이관 → 계약·이슈 운영** (2026-08-06 재설계 — 계약/사이트/이슈 3층) — PM이 완료 상태에서 이관(D1-1): 계약 필수 정보(계약명·기간·금액·사이트 1개 이상 + 각 사이트 **engineerId**)와 함께 Contract+Site 생성·상태 전이가 **한 트랜잭션**, 필수값 누락은 `400`에 전이도 미발생(D1-3). 미완료 이관은 `409 NOT_COMPLETED`(D1-2). 이후 운영은 이슈로 — 등록 시 담당 기본값 = 사이트 engineerId(D3-1), 상태 흐름 접수→처리중→(고객확인대기)→완료(D3-2), 코멘트는 append-only(D3-3 — 수정·삭제 API 없음, 구 MaintenanceLog 불변식 계승). 유지보수 탭의 원천은 프로젝트가 아니라 **계약 목록**(D4-1 — 전사 조회 D4-3)이고, 프로젝트 목록 탭은 `?phase=` 파생 필터(영업/솔루션 — PRD-pms §5)다. 이관 시연 대상 = **명화공업**(시드 확정 2026-08-10 — `maintenance.json` 신규 예정 섹션에 계약 실재, 수주확정→진행중→완료→이관 전체 경로가 이 한 앵커로 이어진다). 이관 없는 입구(직접 등록)와 이슈 운영 일상은 **WS-07**이 커버한다.

### WS-02 역할 지정·교체 (US-A6)

- PM 전세아가 명화공업에 PL로 조예아 추가 → 두 번째 PL 추가도 정상 동작(2026-08-06 PL 복수 허용 — 상위 §4-2, 구 `MULTIPLE_PL` 차단 삭제).
- PL 조예아가 PM 교체 시도 → `403`(A6-2). PM 교체는 현 PM만(A6-1) — ADMIN은 치환으로 자동 포함(상위 §4-1).
- (2026-08-06 신설) PM 전세아가 **권한 패널**(US-A8)에서 이 프로젝트의 역할별 권한 조정 — PL에 배정 권한 확장(A8-6) 또는 참여자 진척률 잠금(A8-5 — 잠그면 웹·챗(SC-11) 모두 403, 동일 서비스 판정). 고정 셀(PM 열·조회·삭제/이관) 수정은 `422 IMMUTABLE_PERMISSION`(A8-4), 조정은 PM만(A8-3), 기본값과 같은 값은 저장하지 않는다(A8-2).

### WS-03 관리자 여정 — 계정·감사 (US-E2 · EPIC H · G1-3)

1. 신현랑(관리자 그룹)이 신규 입사자 등록(E2-1) — 계정은 부록 B 규칙(email 로그인 + 초기 비밀번호 `proten1!`)으로 생성. "사용자/조직/권한 관리" 플래그 없는 그룹의 사용자 관리는 `403`(E2-4 — 2026-08-09 ⑦ 이후 판정은 그룹 플래그, 기본 그룹에선 관리자만 on).
2. 신규 입사자 첫 로그인 → 비밀번호 변경(H1-3) · 알림 설정(H1-4). email 변경 시 중복이면 `409 DUPLICATE_EMAIL`(H1-2).
3. 신현랑이 감사 로그 화면(G1-3)에서 WS-01 5단계의 진척률 변경 이력(누가·언제·무엇을) 추적 — 챗 경유 수정(SC-10)도 같은 AuditLog에 남는지가 검증 포인트. (2026-08-06 신설) 프로젝트 화면의 **프로젝트별 이력**(US-G2)은 같은 AuditLog 행의 `projectId` 필터 뷰(이중 저장 없음 — G2-1)로, 가시성 안이면 역할 무관 조회 가능(G2-3) — 통합로그 G1-3은 ADMIN 전용 유지.

### WS-05 웹 권한 경계 — "챗에서 보이는 것 = 화면에서 보이는 것"

- 서지람이 타 부문 프로젝트 상세 URL 직접 접근 → `404`(A3-2 은닉) — 챗 SC-14와 **같은 서버 판정**.
- 곽서호가 역할 없는 팀 프로젝트의 정보 수정 시도 → `403`(A5-3 취지) — 챗 SC-13과 동일. 반면 진행률은 배정자라면 가능(US-A2 — 기본값 매트릭스 전제, 권한 커스텀 프로젝트는 그 매트릭스가 판정 기준 · A8-5).

- 웹·챗이 동일 애플리케이션 서비스를 쓰므로 이 세 판정이 두 채널에서 갈라지면 구조 원칙 3 위반이다.

### WS-06 동시 수정 충돌 (웹)

### WS-07 유지보수 운영 여정 — 직접 등록·이슈 처리·전사 조회 (US-D2~D4) (2026-08-10 신설)

WS-01 6단계가 이관 입구를 커버하므로, 이 여정은 유지보수 재설계(2026-08-06)의 나머지 절반 — **원천 프로젝트 없는 계약(직접 등록)과 이슈 운영 일상** — 을 검증한다. 앵커는 시드 실데이터(`reference/seed/maintenance.json` — 2026-08-10 확정, 부록 B): 유지보수 운영 조직 = **CS사업팀**(팀장 박건랑(25) · 실무 노도온(26)·한은율(27)·송수람(28)).

1. **직접 등록 (입구 2)** — OEM 채널 계약은 원천 프로젝트가 없다(US-D2 신설 사유): 박건랑(기본 그룹 팀장 — "계약 관리" 플래그 on)이 신규 예정 계약(예: ㈜가온아이 "그룹웨어 구축" — 사이트 유한양행)을 sourceProjectId 없이 등록(D2-1) → 사이트에 engineerId 지정(D2-4). 실무 노도온(팀원 그룹 — 플래그 없음)의 계약 등록 시도는 `403`(D2-3) — 계약은 프로젝트 밖 행위라 그룹 플래그가 판정한다(상위 §4-3). 삭제 API는 없고 계약 종료는 상태{종료}로(D2-2 — 연 단위 갱신 이력 보존).
2. **이슈 등록 → 기본 배정** — 이슈 등록은 로그인 사용자 전체(US-D3): 가온아이 "그룹웨어 유지보수" 계약(사이트 45개 — 계약:사이트 1:N의 극단 실측)의 한 사이트에 이슈 등록(D3-1, type은 시드 이슈 14건과 동일 분류 {장애·문의·요청}) → **assigneeId 기본값 = 해당 사이트 engineerId** + 담당자 알림(`MaintenanceIssueRegistered` — §8 이벤트). 구 게시판 실측(열린 이슈 23건 중 할당 1건 — 사실상 무배정 운영)이 이 기본값의 존재 이유다.
3. **처리 흐름 · append-only** — 담당 노도온이 "내 담당 열린 이슈"를 조회 한 번으로 확보(D3-4 — **미배정(assigneeId=null) 필터** 포함: 신규 예정·종료 사이트는 시드에서 engineerId=null이라 미배정 시연 데이터 겸용), 상태는 접수→처리중→(고객확인대기)→완료·역방향은 재개(완료→처리중)만(D3-2), 조치 내용은 코멘트 **append-only**(D3-3 — 수정·삭제 API 없음, 보정은 새 코멘트로만: 구 MaintenanceLog 불변식 계승).
4. **전사 조회** — 타 부문 서지람(AI팀)이 유지보수 탭에서 계약 목록·상세(사이트 engineerId·연락처·이슈 요약)를 그대로 본다(D4-1·D4-2) — 조직 가시성 미적용·404 은닉 없음(D4-3, 게이트 P에서 확인). **WS-05와 의도된 대조**: 프로젝트는 가시성 은닉(A3-2), 유지보수 계약·이슈는 팀 경계 없는 회사 공용 자산.
