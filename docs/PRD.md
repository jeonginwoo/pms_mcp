## 1. 제품 정의

- **PMS**: 여러 고객사 프로젝트를 인력(M/M)·가동률·유지보수 이력 관점에서 관리하는 사내 도구. 스프레드시트를 대체한다. — 상세: `PRD-pms.md`
- **AI 어시스턴트**: PMS 데이터를 자연어로 조회하고 본인 진척률을 수정하는 사내 챗봇. 표현 다양성을 의도로 접는 일은 LLM이, 계산·권한·데이터 접근은 PMS 로직(결정론)이 담당한다. — 상세: `PRD-host.md`
- **관계**: AI 호스트 Boot 앱(에이전트 루프·LLM·MCP 클라이언트) ↔ PMS Boot 앱 내 임베디드 `/mcp` 어댑터. 구조 원칙 7개는 루트 `CLAUDE.md`가 원본.

## 3. 용어 정의 (공통)

| 용어 | 정의 |
|------|------|
| M/M | Man-Month. 배정 강도 단위 (예: 0.5MM = 월 절반 투입) |
| 배정 M/M | **실투입 계획**(1.0 = 해당 월 풀타임) — **계약 배분 숫자가 아니다**(2026-08-10 재정의, **MCP 담당 확인 완료 2026-08-10**). 계약 관점 수치는 프로젝트 레벨 `contractMm`에만 존재. PM이 입력·유지하며, 체크만 하는 역할은 0에 가깝게 넣는 것이 맞다(PM 자동 배정 기본값 0 — PRD-pms A6-7) |
| 가동률(기본) | 당월 배정 M/M 합 ÷ 가용 M/M(capacity) × 100 (%). **과부하 판정·팀/부문/전사 집계의 정본**(2026-08-10) |
| 보정 가동률 | 단가 가중 투입 — Σ(배정MM × gradeCoeff) ÷ 가용MM × 100. 예: 책임(coeff 1.2), 배정 0.5+0.7, 가용 1.0 → 기본 120% / 보정 144% (PRD-pms AC C1-2와 동일 수치. 직급계수 값은 시드 — §5). 경영 관점 보조 지표로, **과부하 판정에 쓰지 않는다**(2026-08-10 재정의 — 구 ÷coeff 산식은 배정 M/M이 단가 기준일 때만 성립. 명칭은 유지, 화면 문구는 PMS 구현 시 재검토) |
| 오버부킹(과부하) | **기본** 가동률 100% 초과 상태 (2026-08-10 — 구 "보정>100" 대체) |
| 가동률 집계 대상 | 팀·부문·전사 단위 **집계의 모집단은 `Person.billable=true`인 인원만** — 대표·지원조직(영업·기획·경영관리 등 프로젝트 미수행 인력)은 제외한다(2026-08-06 확정 — 시드 실측: 진행중 배정 인원 18/44, 미배정 지원 인력의 0%가 평균을 왜곡. **MCP 담당 확인 완료 2026-08-06**). 개인 단건 조회는 billable 무관. 팀별 false 지정은 시드 적재 규칙(PRD-pms 부록 B) |
| version | 수정 가능 엔티티의 낙관적 락 버전 번호. 쓰기 시 필수, 불일치는 409 → 재확인 절차 |

## 4. 권한 모델

두 축을 **절대 하나로 합치지 않는다**. 서버가 최종 판정하고, 프론트·챗은 노출 제어만 한다. **챗에서 보이는 것 = 화면에서 보이는 것.**

| 축 | 값 | 결정 | 소유 모듈 |
|----|----|------|-----------|
| 조직 가시성 (**권한 그룹** — 2026-08-09 일반화) | 그룹별 가시성 scope 4단: **전사 / 자기 부문 / 자기 팀(하위 조직 subtree 포함) / 본인 참여**. 그룹은 편집 가능(§4-3) — 시드의 orgRole 4종은 기본 그룹 4종으로 적재: 관리자(ADMIN)=전사 · 부문장=부문 · 팀장=팀 · **팀원=자기 팀**(2026-08-22 결정 — 구 "본인 참여"에서 변경. 팀 동료조차 조회할 수 없어 실무와 어긋났다. scope 4단 자체는 그대로이고 기본 그룹의 값만 바뀐다) | 무엇이 보이나 | person(구 identity — 2026-08-21 개명) |
| 프로젝트 역할 | PM / PL / 참여자 — **프로젝트마다 개별 판정한다. 전역 역할이 아니다.** | 그 프로젝트에서 무엇을 할 수 있나 | project |

### 4-1. 판정 규칙 — 합집합 (2026-08-03 확정)

```
canDo(user, project, action)
  = orgPerm(user.group, action)                            // 권한 그룹의 기능 플래그 (§4-3 — 2026-08-09 일반화)
  OR projectPerm(project, roleOf(user, project), action)   // 그 프로젝트의 권한 매트릭스 (§4-2 기본 표 + 프로젝트별 커스텀)
```

- **권한 그룹을 선행 게이트로 쓰지 않는다.** 프로젝트 역할은 조직 기준 권한을 **위로만** 덮어쓴다(축소는 하지 않는다).
- **프로젝트 범위 행위에 대해 `orgPerm`은 공집합이다** — 그룹 플래그가 판정하는 행위는 §4-3의 프로젝트 밖 행위뿐이므로, 프로젝트 안에서는 사실상 `canDo = projectPerm`이 된다. 합집합 형태를 유지하는 이유는 §4-3 행위와 판정식을 하나로 쓰기 위함이다. 단 **전 프로젝트 관리 플래그는 예외** — 아래 참조.
- **"전 프로젝트 관리" 플래그(§4-3)가 켜진 사용자는 모든 프로젝트에서 PM으로 간주한다** — `roleOf(그 사용자, 임의 프로젝트) = PM`. 배정 여부와 무관하며, 조직 관리자가 PM 부재·퇴사 상황을 수습할 수 있어야 하기 때문이다. 이 치환 하나로 §4-2 표가 그대로 적용되므로 표에 별도 열을 두지 않는다. 기본 그룹 중에서는 **관리자 그룹만** 이 플래그가 켜져 있다 — 본 문서·PRD-pms의 "ADMIN 치환" 표기는 전부 이 플래그 치환을 뜻한다(2026-08-09 일반화 이전 표기 유지).
- 근거: 시드 382건 중 **91건(24%)** 이 PM(`managerId`)의 orgRole = MEMBER다. orgRole을 먼저 검사하면 이 91건이 전부 막힌다. 구 `frontend/` 프로토타입에 같은 결함이 있었다 — `canEdit`은 `hasPerm('editProgress')`(orgRole)를 먼저 보고 `canManage`는 `p.pmId === u.id`(PM)를 먼저 봐서 두 판정이 비대칭이었고, PL 개념 자체가 없었다(구 `frontend/src/store.jsx`). **2026-08-22 실연동 재작성에서 해소** — 현행 `frontend/src/permissions.ts`는 `myRole()` 하나(배정이 정본 + "전 프로젝트 관리" 플래그의 PM 치환)를 네 판정이 공유하므로 비대칭이 생길 자리가 없다. 화면 판정은 표시용이고 최종 판정은 서버(`ProjectActionPermission`)다.
- 구 프로토타입의 orgRole별 **프로젝트 스코프** 기능 플래그(`viewAll`·`editProgress` 등 5종)는 미채택(2026-08-03)이며 이 결정은 유지된다 — 권한 그룹(2026-08-09)의 플래그는 **프로젝트 밖 행위 4종만** 담는다(§4-3). 특히 **부문장 `editProgress:false` 폐기는 그대로** — 프로젝트 안 권한은 §4-2가 전담하고, 그룹이 프로젝트 안으로 손을 뻗는 유일한 경로는 "전 프로젝트 관리" 치환뿐이다.

### 4-2. 프로젝트 역할 (project 모듈)

프로젝트당 **PM 1명 필수 · PL 0명 이상 · 참여자 0명 이상**. PM·PL도 배정된 인원이다 — 시드에서 `assigneeIds`가 비어 있지 않은 305건 전부 `managerId` ∈ `assigneeIds`이며, 나머지 77건은 PM이 유일 참여자다.

아래 표는 역할별 권한의 **기본값**이다 — 프로젝트별 커스텀은 표 아래 참조 (2026-08-06).

| 기능 | PM | PL | 참여자 |
|------|----|----|--------|
| 해당 프로젝트 조회 | O | O | O |
| 프로젝트 정보 수정 | O | O | ✕ |
| 인력 배정 / M/M 입력 | O | ✕ | ✕ |
| 진척률 수정 | O | O | O |
| 완료 처리 (진행중→완료 — 진행률 100% 전제) | O | O | O |
| 재개 (완료→진행중) | O | O | O |
| 프로젝트 삭제 | O | ✕ | ✕ |
| 유지보수 이관 | O | ✕ | ✕ |

진척률은 `Project.progress` **단일 값**이므로 "본인 몫만"이라는 부분 수정 개념이 없다(`ProjectAssignment`에 progress 필드 없음). 참여자는 본인이 배정된 프로젝트의 진척률을 수정할 수 있고, 미배정 프로젝트는 애초에 판정 대상이 아니다 — 기존 US-A2·`update_progress` 동작과 동일하다. 모든 진척률 쓰기는 2단계 확인 + `version` 낙관적 락을 거친다.

**완료·재개 (2026-08-06 확정 — MCP 담당 확인 완료)**: 진행률 100% 저장은 완료를 자동 전이시키지 않는다 — **완료 처리는 명시적 행위**이며, 진척률과 같은 실무 경로이므로 배정 전원이 수행한다. 근거: ①자동 전이는 참여자의 진척률 쓰기가 상태 전이 권한(US-A5)을 우회하는 부수효과였고 ②실무에서 100% ≠ 완료(검수·납품 잔여)이며 ③완료를 PM에 묶으면 시드 PM 편중(1인 128건)에서 병목이 된다. **재개**(완료→진행중)는 역방향 금지 불변식의 유일한 예외로, 완료 처리와 같은 권한(배정 전원)이다 — 사고를 낼 수 있는 사람이 수습도 할 수 있어야 한다. 재개 시 진행률은 90으로 되돌린다. **완료 상태의 진척률 직접 수정은 거절(409)** — 재개 후 수정한다. 유지보수중으로 이관된 뒤에는 재개 불가. 상세 AC는 PRD-pms US-A7.

PL은 일정·진척은 다루되 자원 배분(배정·M/M)은 PM에 묶는다 — 오남용 위험이 큰 쓰기 경로를 한 역할로 좁혀 감사 추적을 단순하게 유지한다.

**프로젝트별 권한 커스텀 (2026-08-06 확정 — MCP 담당 확인 완료)**: 위 표는 기본값이며, **PM이 프로젝트 설정에서 프로젝트 단위로 조정**할 수 있다(역할별 기능 토글). 전역 권한 관리 화면은 두지 않는다 — 프로젝트 역할은 프로젝트마다 개별 판정하므로(§4 표) 관리 UI도 같은 스코프에 둔다. 상세 AC는 PRD-pms US-A8.

- **조정 가능**: PL·참여자 열의 {정보 수정 · 인력 배정/M/M · 진척률 수정 · 완료 처리·재개} — 확장(예: PL에 배정 위임)·축소(예: 참여자 진척률 잠금) 양방향
- **고정(토글 불가)**: ①**PM 열 전체** — 매트릭스를 고치는 역할이 스스로 잠기면 복구 불가하고, ADMIN 치환(§4-1)의 수습 보장도 이 열이 전제다 ②**조회 행** — 배정=조회는 가시성(§4-4)의 전제 ③**삭제·유지보수 이관 행** — 비가역 행위의 안전장치(2026-08-06 완료 전이 재설계가 이관을 PM 전용으로 남긴 근거 유지)
- **삭제 권한 확장 (2026-08-22 결정)**: 위 표의 삭제는 PM 외에 **"프로젝트 생성" 플래그 보유자**(기본 그룹 관리자·부문장·팀장)에게도 열린다 — 만든 사람이 지울 수 있어야 한다는 실무 요구. 판정은 `PM 역할 OR 생성 플래그`의 합집합이고, **PL·참여자는 그대로 ✕**다. 프로젝트별 커스텀 대상이 아닌 고정 행이라는 성격은 유지된다(토글로 열거나 닫을 수 없다). 삭제는 soft 삭제이며 배정·감사 이력은 보존된다(PRD-pms A4-1)
- **완료 처리·재개는 한 토글로 묶는다** — "사고 낼 수 있는 사람이 수습도 해야 한다"는 대칭(위 완료·재개 근거)을 프로젝트별 커스텀이 깨지 못하게 한다
- **역할 자체의 추가·삭제는 없다** — 3단 고정. 커스텀 역할 신설은 Out of Scope(PRD-pms §1)
- 판정: §4-1의 `projectPerm`은 이 프로젝트별 매트릭스를 참조한다(커스텀 없으면 기본 표). 변경은 감사 로그에 남기고(PRD-pms G1-1) 기본값 복원을 제공한다
- **MCP 영향**: 도구 카탈로그·`update_progress` 시그니처 변경 없음. 거동 변화 하나 — 참여자 진척률 수정을 끈 프로젝트에서는 `update_progress`가 403이 되고 챗은 거절을 전달한다(권한 판정은 서버가 쓰기 시점에 최종 수행 — 기존 결정과 동일 논리). **기본값에서는 현행과 완전 동일**하므로 기존 시나리오·eval 기대값 무변경

**지정·교체**: 생성 시 PM 필수 지정(생성자 본인이 아니어도 된다), PL은 선택. PM 교체·PL 추가·제거 모두 **PM**이 수행한다 — ADMIN은 §4-1 치환으로 자동 포함된다. 모든 변경은 감사 로그에 남긴다(PRD-pms G1-1). 상세 AC는 PRD-pms US-A6.

**PL 복수 (2026-08-06 확정 — 허용)**: 실무 확인 결과 다부문 프로젝트(4개 팀 걸침)에서 파트별 리드가 실제로 존재한다 — API 제약(구 PRD-pms A1-7)을 해제한다. 스키마는 처음부터 복수를 수용했으므로 마이그레이션·접점 변경 없음.

**유지보수 이력·이슈 (2026-08-06 유지보수 재설계 — MCP 담당 확인 완료)**: 구 표의 "유지보수 이력" 항목은 표에서 제거 — 유지보수는 계약(Contract) 스코프 도메인으로 프로젝트 역할 판정 대상이 아니다(OEM 채널 계약은 원천 프로젝트 자체가 없다 — PROGRESS 결정 기록). 계약 등록·수정은 §4-3(그룹 "계약 관리" 플래그), 이슈 등록·처리·조회는 전사 — 상세는 PRD-pms EPIC D. **이관**은 비가역 행위라 PM 전용·고정 행 유지(위 커스텀 고정 규칙 ③과 정합).

### 4-3. 조직 권한 — 권한 그룹의 기능 플래그 (person 모듈, 2026-08-09 일반화)

프로젝트가 아직 없거나 조직 전체를 다루는 행위는 **권한 그룹의 기능 플래그**가 판정한다(구 orgRole 고정 열거 대체 — 게이트 P 리뷰 결정 ⑦). 프로젝트 범위 행위는 §4-2가 판정하며, "전 프로젝트 관리" 플래그만 §4-1의 치환으로 그 표에 들어간다.

| 플래그 | 판정하는 행위 | 기본 그룹 값 |
|------|------|------|
| 프로젝트 생성 | `POST /projects` | 관리자 · 부문장 · 팀장 |
| 계약 관리 | 유지보수 계약·사이트 등록/수정 (2026-08-06 — MCP 확인 완료) | 관리자 · 부문장 · 팀장 |
| 전 프로젝트 관리 | 모든 프로젝트에서 PM 간주 (§4-1 치환) | 관리자만 |
| 사용자/조직/권한 관리 | 사용자 CRUD · 조직 트리 · 직급 · 권한 그룹 관리 · 통합 감사 조회 | 관리자만 |

- **그룹은 편집 가능**: 신설·수정·삭제(소속 인원이 있으면 삭제 거절). 판정·가시성·404 은닉이 전부 그룹 정의를 따른다 — 그룹 수정은 즉시 반영. 사용자별 그룹 부여는 사용자 관리 경로. 상세 AC는 PRD-pms US-E5.
- **관리자 그룹은 시스템 고정**(수정·삭제 불가) — 자기 잠금 방지. 프로젝트별 권한 커스텀의 "PM 열 고정"(§4-2)과 같은 원리다.
- **시스템 관리자 계정 (2026-08-09)**: `admin@proten.co.kr` — 관리자 그룹 소속의 회사 고유 계정. 삭제·수정 불가, 인력·가동률·배정 목록에서 제외. 감사 actor·수습 주체를 개인(대표) 퇴사와 절연한다. 대표 개인의 관리자 그룹 소속은 유지.
- 그룹에 서열은 정의하지 않는다 — 플래그로만 판정한다.
- **조직 구조 (2026-08-09)**: 회사(root) → 부문 → 팀 → 임의 깊이 트리(구 부문·팀 2단 고정 해제 — PRD-pms §4 `OrgUnit`). 가시성 scope의 "부문" = 소속 경로상 최상위 부문 노드의 subtree, "팀" = 소속 노드의 subtree(하위 조직 포함).

### 4-4. 가시성

```
가시성 = 조직 가시성(권한 그룹의 scope — §4 표. 팀 scope는 하위 조직 subtree 포함)
       ∪ 내가 PM·PL·참여자인 프로젝트
       ∪ 그 프로젝트의 배정 레코드(타 팀 인원 포함)
       ∌ 그 사람의 해당 프로젝트 밖 데이터
```

PM·PL은 프로젝트 컨텍스트 안에서만 타 조직 인원을 본다. 그 인원의 다른 프로젝트나 개인 전체 가동률은 조직 가시성 규칙을 그대로 따른다 — `get_utilization`·`find_person` 응답에 동일하게 적용된다.

- **가시성 밖 = 404 은닉**: 서버는 권한 밖과 부재를 구분해 주지 않는다(구조 원칙 3). 목록은 가시성 내 부분집합만, 단건은 404 — 화면·API·챗 응답 모두 동일 의미론.
- 관리자 그룹(구 ADMIN)=전사 가시성은 시드 orgRole(대표이사 1명)을 근거로 2026-08-02 추가 — **게이트 P에서 최종 승인**(2026-08-09). 권한 그룹 일반화 후에는 관리자 그룹의 scope=전사가 이를 계승한다.
