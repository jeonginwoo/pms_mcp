## 1. 제품 정의

- **PMS**: 여러 고객사 프로젝트를 인력(M/M)·가동률·유지보수 이력 관점에서 관리하는 사내 도구. 스프레드시트를 대체한다. — 상세: `PRD-pms.md`
- **AI 어시스턴트**: PMS 데이터를 자연어로 조회하고 본인 진척률을 수정하는 사내 챗봇. 표현 다양성을 의도로 접는 일은 LLM이, 계산·권한·데이터 접근은 PMS 로직(결정론)이 담당한다. — 상세: `PRD-host.md`
- **관계**: AI 호스트 Boot 앱(에이전트 루프·LLM·MCP 클라이언트) ↔ PMS Boot 앱 내 임베디드 `/mcp` 어댑터. 구조 원칙 7개는 루트 `CLAUDE.md`가 원본.

## 3. 용어 정의 (공통)

| 용어 | 정의 |
|------|------|
| M/M | Man-Month. 배정 강도 단위 (예: 0.5MM = 월 절반 투입) |
| 가동률(기본) | 당월 배정 M/M 합 ÷ 가용 M/M(capacity) × 100 (%) |
| 보정 가동률 | 기본 가동률을 직급계수(gradeCoeff)로 보정 — Σ배정MM ÷ (가용MM × coeff) × 100. 예: 책임(coeff 1.2), 배정 0.5+0.7, 가용 1.0 → 기본 120% / 보정 100% (PRD-pms AC C1-2와 동일 수치. 직급계수 값은 시드 — §5) |
| 오버부킹(과부하) | 보정 가동률 100% 초과 상태 |
| version | 수정 가능 엔티티의 낙관적 락 버전 번호. 쓰기 시 필수, 불일치는 409 → 재확인 절차 |

## 4. 권한 모델

두 축을 **절대 하나로 합치지 않는다**. 서버가 최종 판정하고, 프론트·챗은 노출 제어만 한다. **챗에서 보이는 것 = 화면에서 보이는 것.**

| 축 | 값 | 결정 | 소유 모듈 |
|----|----|------|-----------|
| 조직 가시성 (orgRole) | ADMIN(대표)=전사 / DIVISION_HEAD(부문장)=자기 부문 / TEAM_LEAD(팀장)=자기 팀 / MEMBER(팀원)=본인 참여 — 시드 `people.json` orgRole과 정합 | 무엇이 보이나 | identity |
| 프로젝트 역할 | PM / PL / 참여자 — **프로젝트마다 개별 판정한다. 전역 역할이 아니다.** | 그 프로젝트에서 무엇을 할 수 있나 | project |

### 4-1. 판정 규칙 — 합집합 (2026-08-03 확정)

```
canDo(user, project, action)
  = orgPerm(user.orgRole, action)                  // 조직 기준 기본값
  OR projectPerm(roleOf(user, project), action)    // 그 프로젝트에서의 역할
```

- **orgRole을 선행 게이트로 쓰지 않는다.** 프로젝트 역할은 조직 기준 권한을 **위로만** 덮어쓴다(축소는 하지 않는다).
- **프로젝트 범위 행위에 대해 `orgPerm`은 공집합이다** — orgRole이 판정하는 행위는 §4-3의 두 가지뿐이므로, 프로젝트 안에서는 사실상 `canDo = projectPerm`이 된다. 합집합 형태를 유지하는 이유는 §4-3 행위와 판정식을 하나로 쓰기 위함이다. 단 **ADMIN은 예외** — 아래 참조.
- **ADMIN(orgRole)은 모든 프로젝트에서 PM으로 간주한다** — `roleOf(ADMIN, 임의 프로젝트) = PM`. 배정 여부와 무관하며, 조직 관리자가 PM 부재·퇴사 상황을 수습할 수 있어야 하기 때문이다. 이 치환 하나로 §4-2 표가 ADMIN에도 그대로 적용되므로 표에 ADMIN 열을 두지 않는다.
- 근거: 시드 382건 중 **91건(24%)** 이 PM(`managerId`)의 orgRole = MEMBER다. orgRole을 먼저 검사하면 이 91건이 전부 막힌다. `frontend/` 프로토타입에도 같은 결함이 있다 — `canEdit`은 `hasPerm('editProgress')`(orgRole)를 먼저 보고, `canManage`는 `p.pmId === u.id`(PM)를 먼저 봐서 두 판정이 비대칭이다(`frontend/src/store.jsx:175-188`. 프로토타입에는 PL 개념 자체가 없다). 재연동 시 합집합으로 통일한다.
- orgRole별 기능 플래그(`viewAll`·`createProj`·`manageProj`·`editProgress`·`manageOrg`)는 채택하지 않는다. 특히 **부문장 `editProgress:false`는 폐기** — 부문장이 PM/PL인 프로젝트에서 모순이 발생한다.

### 4-2. 프로젝트 역할 (project 모듈)

프로젝트당 **PM 1명 필수 · PL 0명 이상 · 참여자 0명 이상**. PM·PL도 배정된 인원이다 — 시드에서 `assigneeIds`가 비어 있지 않은 305건 전부 `managerId` ∈ `assigneeIds`이며, 나머지 77건은 PM이 유일 참여자다.

| 기능 | PM | PL | 참여자 |
|------|----|----|--------|
| 해당 프로젝트 조회 | O | O | O |
| 프로젝트 정보 수정 | O | O | ✕ |
| 인력 배정 / M/M 입력 | O | ✕ | ✕ |
| 진척률 수정 | O | O | O |
| 프로젝트 삭제 | O | ✕ | ✕ |
| 유지보수 이관/이력 | O | ✕ | ✕ |

진척률은 `Project.progress` **단일 값**이므로 "본인 몫만"이라는 부분 수정 개념이 없다(`ProjectAssignment`에 progress 필드 없음). 참여자는 본인이 배정된 프로젝트의 진척률을 수정할 수 있고, 미배정 프로젝트는 애초에 판정 대상이 아니다 — 기존 US-A2·`update_progress` 동작과 동일하다. 모든 진척률 쓰기는 2단계 확인 + `version` 낙관적 락을 거친다.

PL은 일정·진척은 다루되 자원 배분(배정·M/M)은 PM에 묶는다 — 오남용 위험이 큰 쓰기 경로를 한 역할로 좁혀 감사 추적을 단순하게 유지한다.

**지정·교체**: 생성 시 PM 필수 지정(생성자 본인이 아니어도 된다), PL은 선택. PM 교체·PL 추가·제거 모두 **PM**이 수행한다 — ADMIN은 §4-1 치환으로 자동 포함된다. 모든 변경은 감사 로그에 남긴다(PRD-pms G1-1). 상세 AC는 PRD-pms US-A6.

**PL 복수**: 스키마는 복수 PL을 수용하되, 실무 확인 전까지 API에서 1명으로 제약해도 무방하다 — 제약 해제 시 마이그레이션·접점 변경이 발생하지 않는 쪽을 택한 것이다.

### 4-3. 조직 권한 — 프로젝트 밖 행위 (identity 모듈)

프로젝트가 아직 없거나 조직 전체를 다루는 행위는 orgRole이 판정한다. (프로젝트 범위 행위는 §4-2가 판정하며, ADMIN은 §4-1의 치환으로 그 표에 들어간다.)

| 행위 | 허용 orgRole |
|------|------|
| 프로젝트 생성 | TEAM_LEAD · DIVISION_HEAD · ADMIN |
| 사용자 · 조직 · 직급 관리 | ADMIN |

orgRole에 서열은 정의하지 않는다 — 열거로만 판정한다.

### 4-4. 가시성

```
가시성 = 조직 가시성(orgRole)
       ∪ 내가 PM·PL·참여자인 프로젝트
       ∪ 그 프로젝트의 배정 레코드(타 팀 인원 포함)
       ∌ 그 사람의 해당 프로젝트 밖 데이터
```

PM·PL은 프로젝트 컨텍스트 안에서만 타 조직 인원을 본다. 그 인원의 다른 프로젝트나 개인 전체 가동률은 조직 가시성 규칙을 그대로 따른다 — `get_utilization`·`find_person` 응답에 동일하게 적용된다.

- **가시성 밖 = 404 은닉**: 서버는 권한 밖과 부재를 구분해 주지 않는다(구조 원칙 3). 목록은 가시성 내 부분집합만, 단건은 404 — 화면·API·챗 응답 모두 동일 의미론.
- ADMIN=전사 가시성은 시드 orgRole(대표이사 1명)을 근거로 2026-08-02 추가 — **게이트 P에서 최종 승인**.

## 6. 협업 접점 (2인 계약 경계)

MCP 도구 카탈로그(`PRD-host.md` §4-2) ↔ PMS 애플리케이션 서비스(`PRD-pms.md` EPIC A·C·D)의 대응이 두 트랙의 계약이다. 어느 쪽이든 접점 변경은 `docs/PROGRESS.md` 결정 기록 경유 + 양측 합의 — 도구명·설명·시스템 프롬프트·Eval 셋은 한 세트로 관리한다(하나를 바꾸면 넷을 같이 바꾼다).
