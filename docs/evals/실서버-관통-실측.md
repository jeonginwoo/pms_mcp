## 1. 전환 구성

| 항목 | 값 |
|---|---|
| `pms.mcp.base-url` | `http://localhost:8080` (목업 8090은 오버라이드로 존치) |
| `/mcp` 인증 | 로그인 access 토큰 — `pms.auth.enabled=false`여도 요구된다(원칙 4) |
| 토큰 발급 | `bash host/scripts/pms-token.sh <personId\|email>` (email·비밀번호는 시드 정본에서 읽는다) |
| 자동 관통 | `(cd host && ./gradlew test -Dpms.real.e2e=true)` → `RealPmsConnectivityIT` 4건 |

**실 토큰에는 `name` 클레임이 없다**(`sub`·`aud=pms`·`token_type=access`뿐). 목업 토큰에는
있었으므로 이것이 전환이 만든 유일한 입력 변화다 — host의 컨텍스트 블록은 `name`이 없으면
`sub`로 폴백해 "대화 상대(사용자): 19"처럼 **숫자**를 주입한다. A-05가 채점하는 것이
`scope=ME` 완결이라 화자 id를 눈앞에 두면 `PERSON, personId=19`로 갈 위험을 먼저 짚었는데,
**실측에서 재현되지 않았다**(§3 A-05 — 3회 전부 `scope=ME`). 지금은 고치지 않고 관찰만 남긴다.

**pms는 기동마다 서명 키를 새로 만든다**(`AuthKeyConfig` ASSUMPTION) — 재기동하면 발급된
토큰이 전부 죽는다. 실측 절차는 케이스마다 토큰을 새로 받는다.

## 2. 도구 흐름을 어떻게 봤나

응답 문장만으로는 **기대 도구 흐름**을 채점할 수 없다. 코드를 더하지 않고 SDK가 이미 내는
로그로 해결했다 — `io.modelcontextprotocol` DEBUG를 켜면
`HttpClientStreamableHttpTransport`가 `CallToolRequest[name=…, arguments={…}]`를,
`McpClientSession`이 응답 전문을 찍는다. 다음 항목(eval 자동 실행 장치)이 쓸 관측 지점도
여기다 — 도구명과 **인자**가 같은 줄에 있어 파라미터 오선택(F5)까지 판정할 수 있다.

## 4. 드러난 결함

### 4-1. A-01 후속의 scope 오선택 (F5 후보 — 카탈로그·프롬프트 몫)

"부문별로 가동률도 정리해줘"를 **`scope=DIVISION`**(= 화자 자기 부문)으로 읽었다.
박재완은 경영관리팀 소속이고 그 부문은 `billable=false`라 결과가 `[]`이고, 답은
"조회 가능한 범위에서 해당 데이터를 찾을 수 없습니다"가 됐다 — **전사를 부문별로 쪼개
달라는 요청에 자기 부문 0건을 답한 것**이다. 2개 대화에서 재현했다.

같은 질문을 "**회사 전체** 이번 달 가동률을 부문별로 정리해줘"로 주면 `COMPANY`를
정확히 고르고 4부문·33명을 앵커대로 답한다(§3). 즉 **카탈로그와 서버는 문제가 없고,
"부문별로"라는 표현이 `DIVISION`으로 끌리는 것**이 원인이다.

고치는 자리는 도구 description(`scope` 낱말 설명)이거나 프롬프트다. **이번 세션에서는
고치지 않았다** — 프롬프트·도구 문구·eval·앵커는 four-in-one이라 한 번에 손대기로 이미
정해져 있고(트랙 파일 "G1 준비 시"), 문구를 지금 바꾸면 eval 셋 전량 재실행 트리거가
걸린다. G1 준비의 첫 후보로 등재한다.

부수 관찰: `[]`에 대한 답 "조회 가능한 범위에서 …찾을 수 없습니다"는 프롬프트 규칙 2의
문구인데, eval 운영 원칙의 **`[]` 유보형 기대값**은 빈 결과를 **권한 제한으로 오진단하면
불합격**이라고 못박고 있다(R3-1). 두 문구 규칙이 빈 집계 응답에서 부딪힌다 — 같은
four-in-one에서 함께 볼 항목이다.

### 4-2. B-01 — 모델이 서버 결과를 스스로 좁혔다 (불합격)

`search_projects(keyword=AI 검색, status=진행중)`은 **정확히 호출됐고 서버는 앵커대로
6건**을 줬다(345 경찰청 · 329 한미글로벌 · 337 국가독성과학연구소 · 332 롯데관광 ·
341 서울시 인재개발원 · 340 한국과학창의재단). 그런데 답은 **2건**이었다 —
"이름에 'AI 검색'이 포함된 프로젝트는 2건입니다"라며 **이름 일치분만 남기고 `solution`
일치분 4건을 버렸다.** B-01의 합격 기준은 개수·목록 일치(허용 오차 0)라 **불합격**이다.

치명은 아니다(없는 것을 만들지 않았고 범위 밖을 노출하지도 않았다 — 축소 방향이다).
`keyword`가 **이름·고객사·솔루션**을 본다는 것은 카탈로그 문구에 이미 있으므로, 모델이
그 문구를 답에 반영하지 못한 쪽이 문제다. 이것도 §4-1과 같은 four-in-one 후보다.

**서버 쪽 오해를 하나 걷어냈다**: 실측 중간에 "실 구현이 `solution`을 안 본다"고 의심했는데
질의는 셋을 다 걸고 있고(`ProjectRepository.search`) 6건이 실제로 온다. 그 6건을
`RealPmsConnectivityIT`에 앵커로 고정했으므로 다음에 같은 의심을 반복하지 않는다.

### 4-3. 빈 응답이 사용자에게 그대로 나갔다 (host 결함 — 이 세션에서 수정)

`/chat`이 `reply: ""`를 반환하는 일이 있었다. 원인은 모델이 아니라 **host였다**:

- 증거 — `finishReason=end_turn` · `completionTokens=606` · **`generations=2`**,
  `[0]` 0자 · `[1]` **295자(정상 답)**.
- `AnthropicChatModel.buildGenerations` 실측(바이트코드 확인): **TEXT 블록은 전부 하나의
  `StringBuilder`로 합쳐져 맨 뒤 generation 하나**가 되고, 앞자리 generation을 갖는 것은
  `thinking`·`redacted_thinking`뿐이다(각각 `signature`·`data` 속성을 달고 온다).
  즉 관측된 `[0]`은 **빈 사고 블록**이었다. `.content()`는 첫 generation만 읽으므로
  사고 블록이 앞에 오면 뒤에 실린 답 전체가 사라진다.
- **목업에서는 드러날 수 없었다** — 응답이 작아 generation이 하나였다.

수정: `ChatService`가 **사고 블록을 걷어낸 뒤 맨 뒤 본문 generation**을 답으로 쓴다.
그래도 비면 빈 문자열이 아니라 안내 문구(`EMPTY_REPLY_NOTICE`)를 주고 `finishReason`·
`usage`를 `EMPTY_REPLY` 키로 warn한다(fail-visible + 러너가 grep으로 구분할 수 있게 —
사용자에게 나가는 문구는 평범한 한국어라 그것만으로는 모델의 무응답과 갈리지 않는다).

**"모든 generation을 이어붙이기"로 갔다가 되돌렸다** — 리뷰에서 잡혔고 바이트코드로
확인했다. 이어붙이면 사고 블록이 비어 있지 않은 순간 **모델의 사고 과정이 사용자 답변
앞에 붙어 나간다.** 실측 당시 `[0]`이 우연히 빈 블록이라 그 실수가 겉으로는 멀쩡해
보였다 — 단위 테스트 3건이 두 방향을 다 고정한다(빈 사고 블록에 답을 잃지 않는다 ·
**사고 내용이 사용자에게 새지 않는다** · 전부 비면 안내 문구).

**이 결함이 실측 전체를 오염시켰을 수 있었다** — A-01 후속이 처음 "빈 응답"으로 보였고
그것을 모델의 회피성 무응답(F6)으로 읽을 뻔했다. 채점 전에 결함을 걷어낸 것이라,
§3의 판정은 수정 후 재실행 결과다.

## 5. 실측이 남긴 상태 변화 (다음 세션 필수 확인)

**쓰기 실측이 시드 DB를 바꿨다** — 사용자 승인 아래 되돌리지 않았다.

| 대상 | 시드값 | 현재 | 영향 |

| 프로젝트 347 `progress` | 5% | **20%** | **eval B-02·D-01의 앵커가 어긋난다**(둘 다 "현재 5%" 전제) |

재앵커 세션이 쓴 절차와 같다. 이것은 다음 항목(eval 자동 실행 장치)의 요구사항이기도
