## 1. 인증 체인 — REST와 같은 검증 지점을 `/mcp`에도

구조 원칙 4(사용자 토큰 패스스루 + audience 제한)의 구현이다. 핵심 설계: **검증 지점은 하나, 그 지점을 통과하는 토큰 유형은 둘**(위임 JWT·PAT). 어느 쪽이든 통과하면 같은 SecurityContext가 서고, 이후 애플리케이션 계층이 평소처럼 권한을 판정한다(합집합 판정 — 상위 PRD §4-1). **MCP용 권한 코드를 한 줄도 새로 짜지 않는다.**

### 1-1. 보안 체인 + audience validator

```java
// mcpconfig/McpSecurityConfig.java
@Configuration
public class McpSecurityConfig {

    @Bean
    @Order(1) // 기존 REST 체인보다 먼저 매칭
    SecurityFilterChain mcpSecurityFilterChain(HttpSecurity http) throws Exception {
        http.securityMatcher("/mcp/**")
            .csrf(AbstractHttpConfigurer::disable)
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(a -> a.anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
        return http.build();
    }

    /** audience 검증 — 이 토큰이 "PMS용"인지 확인해 토큰 전용(오용)을 차단 */
    @Bean
    JwtDecoder jwtDecoder(@Value("${pms.auth.jwks-uri}") String jwksUri) {
        NimbusJwtDecoder decoder = NimbusJwtDecoder.withJwkSetUri(jwksUri).build();
        OAuth2TokenValidator<Jwt> audience = jwt ->
            jwt.getAudience().contains("pms")
                ? OAuth2TokenValidatorResult.success()
                : OAuth2TokenValidatorResult.failure(
                      new OAuth2Error("invalid_token", "audience mismatch", null));
        decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
            JwtValidators.createDefault(), audience));
        return decoder;
    }
}
```

의존성은 `spring-ai-starter-mcp-server-webmvc` + `spring-boot-starter-oauth2-resource-server`(pms), 버전은 `spring-ai-bom:2.0.0`으로 관리한다.

**토큰 유형 검증(2026-08-18 추가 — JWKS 전환분)**: 체인은 audience에 더해 `token_type` 클레임을 허용 목록으로 검증한다 — 허용 = **무클레임**(1-2 위임 JWT·HS256 테스트 토큰) · **`access`**(PMS-M1a 로그인 발급) · **`pat`**(1-3), 그 외 유형은 거절(fail-closed). 근거: 로그인 발급 refresh 토큰(14일 장수명)도 `aud=pms`·정상 서명이라 이 검증 없이는 `/mcp`를 통과한다(REST 체인은 `token_type=access` 강제로 이미 차단 — 비대칭 구멍). 실코드 = `McpSecurityConfig.pmsTokenTypeValidator`, 고정 테스트 = `McpJwksAuthTest`.

### 1-2. 토큰 유형 ① — BFF 위임 JWT (내장 챗 경로)

챗 위젯은 AI 호스트를 직접 부르지 않고 항상 PMS chat BFF(`POST /api/chat` — PRD-pms §7)를 거친다. BFF가 위임 토큰을 발급해 호스트로 넘기는 지점이 레이트리밋·입력 차단·감사 표식의 관문이다.

```java
// pms: chat BFF — 위임 토큰 발급 지점
@PostMapping("/api/chat")
public ChatResponse chat(@RequestBody ChatRequest req, Authentication auth) {
    validator.maxLength(req.message(), 2_000);            // FR-AI-02: 모델 도달 전 차단
    rateLimiter.check(auth.getName());                    // FR-AI-06: 일 50질의 소프트 리밋
    String delegated = tokenService.issueDelegated(auth); // 아래 클레임 규칙
    return aiHostClient.chat(req, delegated);
}
```

위임 JWT 클레임 규칙: `sub`=사용자 · `aud=pms` · **만료 5분(단명)** · `channel=ai-assistant`(감사 표식 — AuditLog `source=MCP` 기록의 근거 클레임, PRD-host §7). 호스트는 이 토큰을 저장하지 않고 그대로 `/mcp` 호출에 싣는다.

### 1-3. 토큰 유형 ② — PAT를 JWT 형식으로 (직접 접속 경로)

표준 MCP 클라이언트(Inspector·Claude 데스크탑 등 파워유저 경로)가 BFF 없이 `/mcp`에 직접 붙을 때 쓴다. 요령: **PAT를 JWT 형식으로 발급**(`sub`=사용자, `aud=pms`, `token_type=pat`, 만료 수개월)하면 1-1의 리소스 서버 체인을 **한 글자도 안 바꾸고** 두 토큰 유형이 같은 검증 지점을 통과한다.

- 취소 가능성: PAT에 `jti`(토큰 ID)를 넣고 발급 목록을 DB에 저장, 검증 시 취소 여부만 추가 대조(기술_선택_근거 §7 "JWT의 대가"에 대한 보완).
- 부록 B의 목업 테스트 토큰이 사실상 이 PAT와 같은 형태다 — 목업에서 검증한 흐름이 실전 PAT 경로로 그대로 이어진다.

### 1-4. 검증 절차 (M0 게이트: 인증 3케이스)

① 토큰 없이 401 ② 타 audience 토큰 401 ③ 정상 토큰으로 `whoami`가 그 사용자를 반환.

```bash
# 방법 1: MCP Inspector (GUI)
npx @modelcontextprotocol/inspector
# Transport: Streamable HTTP, URL: http://localhost:8080/mcp
# Authorization 헤더에 Bearer <테스트 JWT> → tools 목록에 whoami 확인

# 방법 2: curl 핸드셰이크 (protocolVersion 2025-11-25 기준)
curl -s -X POST http://localhost:8080/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"test","version":"0.1"}}}'
```

> **stateless 지향 주의(구조 원칙 7):** 2025-11-25 스펙에서는 initialize 핸드셰이크와 `Mcp-Session-Id`가 프로토콜에 존재한다 — SDK가 요구하는 만큼만 따르되, **우리 도구·설계가 세션 상태에 의존하는 코드를 만들지 않는다**(요청 간 서버 상태 무). Spring AI 2.0의 서버 스타터에는 `protocol: STATELESS` 옵션도 있다 — Java SDK가 2026-07-28 신 스펙을 지원하면 이 절(핸드셰이크 절차 포함)과 전환 여부를 갱신한다(PROGRESS 미해결 이슈의 모니터링 항목).

## 2. 예외 → 도구 에러 매핑

애플리케이션이 던지는 기존 예외를 도구 에러로 일관 변환한다. 목적은 두 가지: ① 모델이 에러 문구를 읽고 **스스로 수정**(재조회·파라미터 변경)할 수 있게 사람이 읽을 수 있는 메시지로, ② 화면과 같은 은닉·권한 규칙을 챗에서도 유지.

| 기존 예외 | MCP 도구 응답 (`isError: true` + 메시지) |
|-----------|------------------------------------------|
| 404 은닉 (범위 밖/부재) | "조회 가능한 범위에서 해당 데이터를 찾을 수 없습니다" — **권한/부재 비구분 문구** (PRD-host S-4·FR-AI-20과 동일 문구로 통일. 구 가이드의 "해당 프로젝트를 찾을 수 없습니다"는 프로젝트 한정이라 폐기) |
| 403 권한 부족 | "이 작업은 해당 권한이 있는 사용자만 가능합니다" + 서버가 판정한 사유 (합집합 판정 — 상위 PRD §4-1. 진척률은 PM·PL·참여자, 정보 수정은 PM·PL 등 도구별 상이) |
| 409 STALE_VERSION | "다른 사용자가 먼저 수정했습니다. 최신값은 N%입니다" — **최신값 동봉** (아래 2-1) |
| 422 검증 실패 | 필드별 사유 그대로 (PRD-pms §6 에러 표의 코드 체계) |
| 5xx / 타임아웃 / 점검 | 표준 형식(오류 코드 + 사용자 안내문 + 재시도 가능 여부) — FR-AI-26. 모델은 부분 결과·학습 지식으로 메꾸지 않고 실패 사실을 안내 |

구현 위치: `@RestControllerAdvice`는 `/mcp`를 타지 않으므로, 도구 내부 공통 헬퍼로 감싸거나 예외를 그대로 던져 SDK의 에러 변환(`isError: true` + 메시지)에 맡긴다. 어느 쪽이든 **문구는 위 표가 정본**이다(프롬프트·Eval 셋이 이 문구를 전제).

### 2-1. 409 재확인 절차 (낙관적 락 — 기술_선택_근거 §8에서 이관)

`update_progress`가 `version` 파라미터를 요구하는 이유가 이 절차다. 조회 도구(`search_projects` 상세)가 `version`을 반환하므로(FR-AI-10) 흐름이 조회만으로 완결된다:

1. 모델이 `search_projects(projectId=A)`로 현재 진행률과 `version`을 확보.
2. `update_progress(confirmed=false, version=...)` → 변경 요약 반환 → 확인 카드.
3. 사용자 [실행] → `confirmed=true` 재호출.
4. 그 사이 남이 수정했으면 서버가 **409 + 최신값**을 반환 → 도구 에러로 전달.
5. 모델은 최신값 기준으로 **재확인을 다시 받는다**: "다른 사용자가 먼저 수정했어요. 최신값은 70%입니다. 다시 진행할까요?" — 임의 재시도(사용자 확인 없이 최신 version으로 재호출) 금지. F3(미확인 쓰기)의 변형이다.

## 3. AI 호스트 구성

### 3-1. `spring.ai.mcp.client.enabled: false`의 이유

```yaml
# host/application.yml (Spring AI 2.0 확정 키 — 2026-08-13 B2-3 구현 검증)
spring:
  ai:
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}
      chat:
        model: claude-sonnet-5   # 기준 모델 — 최종 확정은 G3 (PRD-host). 2.0에서 chat.options.* 는 deprecated
```

B2-3 구현은 한 걸음 더 가서 **클라이언트 스타터 자체를 넣지 않았다**(`spring-ai-mcp` 라이브러리만 의존) — 자동 구성이 클래스패스에 없으므로 `spring.ai.mcp.client.enabled: false`조차 불필요하다. 스타터를 쓰는 프로젝트라면 이 키로 끈다.

`spring.ai.mcp.client.streamable-http.connections.*`로 선언하는 부트 자동 구성은 앱 전체가 **하나의 고정 연결**을 공유하는 모델이다. 우리는 요청마다 **그 사용자의 토큰**으로 PMS를 호출해야 하므로(전능한 서비스 계정 금지 — 구조 원칙 4) 자동 구성이 성립하지 않는다. 연결을 요청/대화 단위로 직접 생성한다.

### 3-2. 사용자 토큰으로 PMS MCP 연결 생성

```java
// host: mcp/PmsMcpConnector.java — 확정 코드 (2026-08-13 B2-3 구현·목업 관통 IT로 검증)
@Component
public class PmsMcpConnector {

    @Value("${pms.mcp.base-url}") // 예: http://pms:8080
    private String pmsBaseUrl;

    /** 사용자 토큰을 실은 MCP 클라이언트. 대화 단위 생성·재사용, 종료 시 close. */
    public McpSyncClient connect(String userToken) {
        var transport = HttpClientStreamableHttpTransport.builder(pmsBaseUrl)
                .endpoint("/mcp")
                // MCP SDK 2.0: customizeRequest()는 제거 — 5인자 McpSyncHttpClientRequestCustomizer
                .httpRequestCustomizer((builder, method, endpoint, body, context) ->
                        builder.header("Authorization", "Bearer " + userToken))
                .build();
        McpSyncClient client = McpClient.sync(transport)
                .requestTimeout(Duration.ofSeconds(30))
                .build();
        client.initialize();
        return client;
    }
}
```

성능이 신경 쓰이면 `conversationId → client` 캐시(만료 시 close)를 두되, 1차 규모(44명)에서는 요청마다 생성해도 충분하다. **캐시를 두더라도 토큰 만료(위임 JWT 5분)보다 오래 재사용하지 않는다.**

### 3-3. 에이전트 루프 — ChatClient + MCP 도구

에이전트 루프(도구 호출 → 결과 반영 → 재호출)는 ChatClient가 내장한다. 호스트가 코드로 강제하는 것은 PRD-host의 입출력 규칙 중 프롬프트만으로 못 지키는 것들이다:

- **대화 이력 최대 10턴** — `MessageWindowChatMemory.maxMessages=20` (턴=질문·응답 쌍, FR-AI-01).
- **오늘 날짜 + 호출자 identity 주입** — 시스템 메시지에 포함. "이번 달"류 상대 시점 해석의 기준이고, identity는 `whoami` 호출을 아끼는 힌트일 뿐 권한 판정 근거가 아니다(판정은 서버 — 구조 원칙 3·4).
- 파일·이미지 입력 미지원, 비밀번호/토큰 패턴 감지 시 무시·경고 (FR-AI-24).

```java
// host: chat/ChatService.java — 확정 코드 (2026-08-13 B2-3 구현으로 검증. 전문은 host/…/chat/ChatService.java)
public String chat(String conversationId, String userMessage, String userToken) {
    try (McpSyncClient pms = pmsMcp.connect(userToken)) {
        var tools = SyncMcpToolCallbackProvider.builder()
            .mcpClients(pms)
            // 2.0 builder 기본값은 접두사 부착 — 프롬프트가 도구명을 그대로 참조하므로 금지
            .toolNamePrefixGenerator(McpToolNamePrefixGenerator.noPrefix())
            .build();                                     // 생성자 직접 호출은 2.0 deprecated
        return chatClient.prompt()                        // chatClient에 메모리 어드바이저 기본 장착
            .system(SystemPrompts.PMS_ASSISTANT + contextBlock(userToken)) // §4 전문 + 날짜·identity
            .user(userMessage)
            .tools(tools)                                 // toolCallbacks(...)는 2.0 deprecated
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, memoryKey)) // key = sub + ":" + 대화 id (화자 간 맥락 격리)
            .call()
            .content();
    }
}
```

## 5. 도구 작성 원칙 (구 가이드 §5-1 승계 — `/mcp` 어댑터 공통)

- **도구 1개 = 유스케이스 1개.** 애플리케이션 서비스 메서드에 1:1 대응. 어댑터는 서비스만 호출한다(구조 원칙 3 — 리포지토리 직접 접근 금지, Modulith/ArchUnit 테스트로 강제).
- description은 **모델이 읽는 문서**다. "언제 쓰는 도구인지, 무엇이 돌아오는지"를 한국어로 명확히. 카탈로그 정본은 PRD-host §4-2 — 여기 있는 것만 노출한다.
- 파라미터는 원시 타입 + 명시적 `@McpToolParam` 설명. 반환은 화면 DTO 재사용 대신 **AI 응답용 얇은 DTO**(토큰 절약 + 과노출 방지). 긴 목록은 서버에서 절단(`list_maintenance_logs` 최근 50건).
- `@McpTool` 빈은 자동 스캔·등록된다(별도 등록 코드 불필요). 서버 설정: `protocol: STREAMABLE` · `type: SYNC`(JPA 트랜잭션과 자연스러움).

## 6. SSE 구현 세부 — 인프라 공통분 (기술_선택_근거 §9에서 이관)

이미터 구성·재연결·미읽음 재조회 등 알림 파이프라인은 **PRD-pms 소유**(US-F1). 여기는 챗 스트리밍과 알림이 공유하는 인프라 공통분만 둔다:

- **프록시 버퍼링 해제**: Nginx가 SSE 응답을 버퍼링하면 "즉시 푸시"가 죽는다. 해당 location에 `proxy_buffering off`(또는 앱이 `X-Accel-Buffering: no` 응답 헤더 송출) + 긴 `proxy_read_timeout`. 챗 진행 상태 표시(FR-AI-03)와 알림 스트림 모두 해당.
- **쿼리 토큰 인증**: EventSource는 커스텀 헤더를 싣지 못하므로 `?access_token=` 쿼리 파라미터로 인증한다(PRD-pms §7). **액세스 로그에 토큰이 남지 않도록 Nginx 로그 포맷에서 마스킹 필수.**
- 재연결 복구는 표준(Last-Event-ID) 기반 — 상세는 PRD-pms.

## 부록 A — AI 호스트 대안: ProLLMOps 판단 (기술_선택_근거 §11-5에서 이관)

사내 ProLLMOps(LLMOps 플랫폼, MCP 게이트웨이로 `runWorkflow` 도구 1개 노출)를 활용하는 두 형태를 검토했다.

**형태 1 — ProLLMOps를 AI 호스트로 (자체 호스트 대체): 보류.** 결격 사유는 인증이다. `runWorkflow` 인자에는 사용자 토큰 자리가 없고(`userId`는 문자열 식별자일 뿐 인증이 아님), 워크플로우의 에이전트가 PMS `/mcp`를 호출할 때 **요청 사용자별 Authorization 헤더를 실어줄 수 있는지 확인되지 않았다.** 이게 안 되면 워크플로우가 고정 자격증명으로 PMS를 부르게 되어 구조 원칙 4(전능한 서비스 계정 금지)와 정면 충돌한다. 대안인 "서비스 토큰 + userId 클레임 대리 판정"(on-behalf-of)은 신원 위조 방지 책임이 PMS로 넘어와 복잡도·위험이 커서 권장하지 않는다.

**형태 2 — ProLLMOps를 보조 도구로 (자체 호스트 유지): 필요 시 채택.** 자체 호스트에 외부 MCP 서버 중 하나로 연결(M3 하이브리드 패턴)해 사규/문서 RAG 질의를 챗에서 함께 쓰는 형태. 읽기 전용 RAG라 토큰 패스스루 문제가 없다(문서 조회 범위가 사용자별이어야 한다면 재검토). 주의: `apiKey`는 모델이 채우게 두지 말고 호스트가 고정 주입한다(도구 래핑으로 `query`만 노출). 외부 도구 결과도 프롬프트 인젝션 벡터다 — 프롬프트 규칙 7 + 외부 전송 작업은 확인 카드 필수.

**결론**: 1차는 자체 Spring AI 호스트(인증 통제 = 이 설계의 성패 지점을 코드로 확보). ProLLMOps가 사용자별 인증 헤더 전파를 공식 지원하면 형태 1을 재검토한다 — 그 경우에도 PMS 쪽(MCP 서버·도구)은 바꿀 것이 없다(역할 배치 구조의 이점). 상세 비교표·게이트웨이 명세는 구 가이드 부록 A(읽기 전용) 참조.

```java
}
```

테스트 토큰은 기본 그룹 4종 대표로 발급(`sub`·`name`·`aud=pms`·`channel=ai-assistant` — `cd pms-mcp-mock && ./gradlew printTestTokens`). **판정에 신뢰하는 클레임은 `sub`뿐**(2026-08-13 구현 실측) — 호출자의 그룹·팀·프로젝트 역할은 서버 쪽 데이터에서 조회한다. 권한 정보를 토큰에 싣지 않는 것이 원칙 3·4 정합이고, 프로젝트 역할 축은 데이터가 담당하므로 역할별 토큰도 불요(당초 "orgRole×프로젝트 역할 조합 발급, 클레임으로 가시성 흉내" 계획을 이 형태로 대체). 검증: MEMBER 토큰과 DIVISION_HEAD 토큰으로 같은 `search_projects` → 결과 집합이 달라야 하고, 가시성 밖 단건 지정은 404 은닉 문구(§2)가 나와야 한다.

**B2-3. 자체 호스트 연결** — host 앱의 `pms.mcp.base-url`만 목업으로 겨눈다. 챗~BFF~호스트~MCP 전 구간을 PMS 없이 관통 테스트.
